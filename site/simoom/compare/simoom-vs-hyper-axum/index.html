hyper and axum vs simoom

hyper is Rust's default HTTP library, and axum is the framework most teams build on top of it, both on tokio. simoom takes a different road: no async runtime, no third-party crates, HTTP/3 and TLS in the box. Benchmark campaign 4 (2026-11-12) measured hyper, axum, axum with rustls, actix-web and simoom on the same droplets in the same rounds. Here is what came out, including where they are ahead.

When to pick hyper or axum instead

For many Rust services, axum on tokio is the right answer, and that is fine.

Pick hyper or axum when

  • Your program is already async and runs on tokio, or uses libraries that need it (database drivers, gRPC, cloud SDKs).
  • You want tower middleware, axum extractors, OpenAPI generators and the rest of the ecosystem.
  • Your team already knows axum, and hiring and onboarding matter more than footprint.
  • You need a library with years of production use and many contributors. simoom is at 0.1.0.
  • You want independently audited TLS: pair hyper with rustls. In campaign 4, axum with rustls also completed 24% more full TLS 1.3 handshakes per second than simoom (11,633 against 9,530).
  • Memory at rest matters more than memory per connection: hyper's idle process used 1,374 KB against simoom's 1,769 KB.

Pick simoom when

  • You don't want an async runtime in a program that never needed one: a CLI, a desktop app, a daemon, a device.
  • Every third-party crate is a review: simoom has none, from the TLS handshake to QUIC.
  • Binary size and start-up count: about 215 KB added for HTTP/1.1; in campaign 4 the default build was 735 KB stripped against hyper's 2,069 KB, and answered its first request 0.94 ms after process start against hyper's 1.48 ms.
  • You want HTTP/3 without a separate experimental stack.
  • Throughput per core matters and you can live with a smaller API.

What the code looks like

No async, no runtime to start. A route is a function that takes the request and a reply.

use simoom::{Outcome, Reply, Request, Router, Server};

let router = Router::new()
    .get("/health", |_: &mut Request<'_>, r: Reply<'_>| r.body_static(b"ok"))
    .get("/users/:id", |req: &mut Request<'_>, r: Reply<'_>| -> Outcome {
        let id = req.param_str("id").unwrap_or("").to_string();
        r.header("content-type", "application/json").body(format!("{{\"id\":\"{id}\"}}"))
    });

let server = Server::builder().listen("0.0.0.0:8080").service(router).start().expect("start");

Slow work (a database query, a call to another service) goes to the bounded offload pool with simoom::blocking, or to your own threads with Reply::defer. See routing and slow work.

How it was measured

Setup

  • DigitalOcean c-4 droplets (4 dedicated vCPUs, Xeon Platinum 8280, Bangalore), Ubuntu 24.04.
  • One server droplet, two separate load droplets, open-loop load: requests arrive at a fixed rate whether or not the server keeps up.
  • hyper 1.12.0, axum 0.8.9, axum-server 0.7.3 with rustls 0.23.46 and actix-web 4.18.2, each from its pinned Cargo.lock; simoom from the measured commit.

Rules

  • Headline: the highest steady rate whose p99 stays at or under 1 ms (5 ms for HTTP/2 with 100 streams and for a new connection per request).
  • Campaign 4, 2026-11-12: simoom ran on the same droplet in the same round as each competitor; every figure is the median of rounds (three or one per measure; the benchmarks list the runs).
  • Only servers on the same droplet are compared; raw HDR logs and scripts are in bench/results/.

Common questions

Is simoom faster than hyper?

In benchmark campaign 4 (2026-11-12), with both servers on the same 4-vCPU droplet in the same rounds, simoom answered 137,889 status requests per second with 99% within 1 ms at 256 clients against hyper's 110,931 (24% more), and used 23.6 µs of CPU per request at a fixed 50,000 req/s against hyper's 32.6 µs (26% less). Of 21 measures simoom was ahead of hyper on 15, level on 5 and behind on 1: hyper's process used less memory at rest (1,374 KB against 1,769 KB). Start-up of simoom's full server (with TLS 1.3 and HTTP/3) was level with hyper, 1.46 ms against 1.48 ms; simoom's default build started in 0.94 ms.

Can I use hyper without tokio?

hyper is built for async Rust and in practice runs on tokio. If the goal is no async runtime at all, simoom is built that way: a service is a plain function on an event loop thread, and slow work goes to a bounded offload pool or to your own threads.

hyper vs axum vs simoom: which should I use?

For a typical web API on tokio with middleware, extractors and a team that knows the ecosystem, axum is the safer choice. For a low-level HTTP library inside the tokio world, use hyper. For an embedded server with no async runtime, no third-party crates, HTTP/3 and a small binary, use simoom.

Does simoom work with tower middleware?

No. simoom has its own Service type, a Router and optional helpers for compression, CORS, cookies, multipart, conditional requests and authentication. It does not implement tower's traits, so tower layers and axum extractors do not plug into it.

Does hyper support HTTP/3?

Not by itself. HTTP/3 for the hyper ecosystem lives in the separate h3 crate, which describes itself as experimental. simoom ships HTTP/3, QUIC v1 and TLS 1.3 in-tree as cargo features.
