A library against two C servers

h2o and nginx vs simoom

nginx and h2o are standalone web servers written in C, with configuration files, static files and proxying. simoom is a library inside your Rust program. They do different jobs, but they all terminate TLS, speak HTTP/2 and serve requests, so benchmark campaign 4 (2026-11-12) measured them side by side, each on the same droplet as simoom. Here is where simoom is ahead, where H2O and nginx are, and how they work together.

Use them together

Most deployments don't have to choose. nginx or h2o can serve static files and route traffic at the edge while simoom answers the dynamic requests inside your program.

Tested behind front servers

  • Request-smuggling test behind nginx 1.24 and haproxy 2.8: 165 attack streams, 0 desyncs, and 0 requests accepted that both front servers refused.
  • HTTP Garden, as an origin next to nginx, Apache httpd, h2o, hyper, gunicorn and Go: 0 desyncs, 0 dangerous discrepancies.
  • Strict parsing per RFC 9110 and 9112: any message whose framing is ambiguous is refused.

Or skip the hop

  • simoom terminates TLS 1.3 and serves HTTP/2 and HTTP/3 itself, on the same port number, announced with alt-svc.
  • Limits, slow-client guards and overload guards are built in, each with a default.
  • Useful where a second process is a cost: a device, a function, a sidecar.

When to pick nginx or h2o instead

Pick nginx or h2o when

  • You need a web server, not a library: static files, a reverse proxy, load balancing, a config file your operations team already knows.
  • Your traffic regularly exceeds what the machine can carry and in-time answers under overload matter most: in campaign 4's traffic spike nginx answered 4.7x as many requests within 1 ms as simoom.
  • HTTP/3 or HTTP/2 throughput is what you need most: H2O answered 43% more HTTP/3 and 11% more HTTP/2 requests than simoom on the same droplet.
  • Your program isn't written in Rust.
  • You want decades of production use and a large operations community.

Pick simoom when

  • HTTP belongs inside your Rust program, not in a separate process.
  • TLS handshake rate and HTTPS throughput matter: 39% / 56% more full / resumed handshakes and 30% more HTTPS requests per second than H2O on the same droplet, and 2.5x nginx's HTTPS throughput.
  • You want HTTP/3 from a library, with no C toolchain and no third-party crates.
  • Start-up time counts: 0.90 ms to the first answer for the default build, against 14.34 ms for H2O and 19.57 ms for nginx.

How it was measured

Setup

  • DigitalOcean c-4 droplets (4 dedicated vCPUs, Xeon Platinum 8280, Bangalore), Ubuntu 24.04.
  • h2o built from master at commit f35c735 (the project has not tagged a release since 2019 and its docs say to build from source); nginx from Ubuntu 24.04's packages, built without HTTP/3.
  • Open-loop load from two separate machines.

Rules

  • Throughput: the highest steady rate whose p99 stays at or under 1 ms (5 ms for 64 KB bodies and HTTP/2 with 100 streams).
  • Handshakes: closed loop, 192 connections.
  • Campaign 4, 2026-11-12: simoom ran on the same droplet in the same round as nginx and H2O; every figure is the median of rounds.

Common questions

How does simoom's TLS performance compare with h2o?

In benchmark campaign 4 (2026-11-12), with both servers on the same 4-vCPU droplet in the same rounds, simoom completed 9,431 full and 10,303 resumed TLS 1.3 handshakes per second against H2O's 6,615 and 6,458 (39% and 56% more), and answered 103,311 HTTPS requests per second with 99% within 1 ms against H2O's 79,386 (30% more). Its peak memory while serving HTTPS was 7,518 KB against H2O's 9,701 KB.

Is h2o or nginx faster for HTTP/3?

H2O. nginx was not measured on HTTP/3: the Ubuntu 24.04 nginx package used in the benchmark has no HTTP/3 support. In benchmark campaign 4 (2026-11-12), on the same droplet in the same rounds, H2O answered 75,055 HTTP/3 requests per second with 99% within 1 ms against simoom's 52,259 (43% more), and used 43% less peak memory doing it. simoom answered 1.65 times as many HTTP/3 requests as quinn with h3 on its droplet.

Can simoom replace nginx?

Not as a web server. simoom is a library you build into a program: it has no configuration file, no static-file server and no reverse proxy. It replaces the HTTP layer inside your program, and nginx or h2o can still sit in front of it.

Can I run simoom behind nginx or haproxy?

Yes. In a request-smuggling test behind nginx 1.24 and haproxy 2.8, simoom saw 165 attack streams with 0 desyncs, and it accepted none of the requests that both front servers refused. In HTTP Garden, as an origin next to nginx, Apache httpd, h2o, hyper, gunicorn and Go, it had 0 desyncs.

Where is nginx better than simoom?

During traffic spikes: at 195,000 requests per second offered, nginx answered 29,135 requests per second within 1 ms against simoom's 6,264 on the same droplet (4.7 times as many), while both answered about 160,000 per second in total. nginx also used 6% less memory per idle connection with 10,000 open (538 against 575 bytes; level at 100,000), and it is a complete web server with years of operations behind it. H2O, for its part, leads HTTP/2 by 11% and HTTP/3 by 43%. Figures: campaign 4, 2026-11-12.

Serve TLS, HTTP/2 and HTTP/3 from your program

Build with --features full. Over TCP, client and server agree on HTTP/2 or HTTP/1.1 during the TLS handshake; the QUIC listener serves HTTP/3 on the same port number.

let server = Server::builder()
    .listen_tls("0.0.0.0:8443").tls(tls.clone())
    .listen_quic("0.0.0.0:8443").quic_tls(tls)   // HTTP/3, announced with alt-svc
    .service(router)
    .start()?;
