HTTP server engine for Rust

The HTTP server you build into your Rust program.

HTTP/1.1, HTTP/2 and HTTP/3, its own TLS 1.3, WebSocket and a client. Nothing underneath but the Rust standard library: no tokio, no hyper, no rustls, no OpenSSL. Write a function that answers a request and call start().

src/main.rs
use simoom::{Outcome, Reply, Request,
             Server, StaticReply};
use std::sync::Arc;

fn main() {
    let hello = Arc::new(StaticReply::new(200,
        &[("content-type", "text/plain")],
        b"Hello, World!"));
    let server = Server::builder()
        .listen("127.0.0.1:8080")
        .service(move |_req: &mut Request<'_>,
                       reply: Reply<'_>| -> Outcome {
            reply.fixed(&hello)
        })
        .start()
        .unwrap();
    server.join(); // one event loop per CPU core
}
cargo add simoom · Rust 1.89+ · Linux, Windows, macOS

You wanted a door. Rust gave you a house.

Most programs that speak HTTP don't want a web server. They want a door: a place where requests come in and answers go out. A sensor reports its readings. A function wakes up, answers one call and goes back to sleep. A desktop app shows a dashboard in the browser. An integration engine takes webhooks all day.

In Rust, that door usually comes with a house attached: an async runtime, a few dozen crates, and a megabyte or more of code you didn't write and can't easily audit.

simoom is just the door.

You add one crate and write a plain function. Underneath, simoom runs one event loop per CPU core on epoll or io_uring (Linux), IOCP (Windows) or kqueue (macOS), and every protocol is a cargo feature, so you pay only for what you turn on.

  • HTTP/1.1keep-alive, pipelining, chunked bodies, strict parsing (RFC 9112)
  • HTTP/2over TLS and without it, with flood protection (RFC 9113)
  • HTTP/3over QUIC v1 on the same port number, announced with alt-svc
  • TLS 1.3its own: X25519, P-256, RSA, AES-GCM; client certificates (mTLS)
  • Live updatesWebSocket (also over HTTP/2 and HTTP/3) and server-sent events
  • Slow worka bounded offload pool that says 503 instead of queueing forever
  • A clientHTTP/1.1, HTTP/2, HTTP/3, pooling, proxies, WebSocket
  • Safetyunsafe in one crate only; every limit has a default

Why it exists: Cameleer needed a better door

Cameleer runs Apache Camel-style integration routes in Rust, with nothing outside the standard library. Its first HTTP server gave every connection its own thread: simple, but heavy. simoom was written from the ground up to replace it, under the same rule, and measured against it on the same machine.

Where simoom is behind

  • Heavy overload: at 1.17 times what the network card can carry, nginx answers 52.4k requests within 1 ms against simoom's 6.4k, although simoom answers more in total (160.3k against 145.5k).
  • A degraded network path: may-minihttp kept 114.7k req/s while simoom and the others fell to 17–62k.
  • A new connection per request: on one droplet xitca handled 24.3k connections per second against simoom's 19.3k.
  • Slow attackers: under slowloris, haproxy's p99 for real requests was 8% lower.

When to use something else

simoom is new, small and focused. Pick the alternative when it fits better.

Quick start: three commands

Add the crate, paste the server above into src/main.rs, run it and send it a request. For HTTP/1.1 only, turn the default features off.

cargo add simoom
cargo run --release
curl http://127.0.0.1:8080/
# Cargo.toml: the smallest build, for a device or a function
simoom = { version = "0.1", default-features = false, features = ["http1"] }

Common questions

Is there a Rust HTTP server without tokio?

Yes. simoom has no async runtime. A service is a plain function that runs on the event loop thread; slow work goes to a bounded offload pool or to your own threads. Streaming, server-sent events and WebSocket all work without async.

Does simoom really have zero dependencies?

Yes. The workspace has no crates.io dependencies at all, not even for tests. TLS 1.3, QUIC, HTTP/2, HTTP/3, the compression codecs and the event loops are all in the repository. It is std-only, not no_std: it needs Linux, Windows or macOS.

How fast is it?

On the same 4-vCPU DigitalOcean droplet, simoom served 172,638 plain requests per second with p99 under 1 ms at 256 connections, against hyper's 144,443 and may-minihttp's 150,673. Over TLS it served 160,441 against h2o's 97,219. It also loses in some scenarios, which are published next to the wins.

Is it a web server like nginx?

No. simoom is a library you build into a program. It has no configuration file, no static-file server and no reverse proxy. For those jobs use nginx, Caddy or h2o.

Is simoom ready for production?

It is at version 0.1.0 and the API can still change. It passes h2spec 146/146, 54 of 58 supported QUIC Interop Runner pairs and HTTP Garden with 0 desyncs, and Cameleer uses it as its HTTP engine. It has not had an independent security audit yet.

A Cameleering project

A simoom is a hot, fast wind that crosses the desert. It travels with Cameleer, the integration engine, under the same practice: Cameleering, making software carry the same load on less and proving every gain against the original, on the same hardware, with the method published.

That is why every number on this site names its machine, its date and its baseline, and why the losses sit next to the wins.

Carry more on less. No claim without a number.
