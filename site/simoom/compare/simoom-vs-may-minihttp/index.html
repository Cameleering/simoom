may-minihttp vs simoom

may-minihttp is a minimal HTTP/1.1 server on the may stackful coroutine library, well known from benchmark tables. In benchmark campaign 4 (2026-11-12) it was the only server ahead of simoom on the status endpoint at 256 clients. Here is where it leads, and where simoom does.

An earlier round

An earlier campaign (campaign 3, 2026-11-11) ran before a fix that keeps simoom's event loops off the CPU busiest with network-card interrupts (bug K12 in the repository), and read differently. Campaign 4 supersedes it; its figures stay in bench/results/2026-11-11-campaign3/ and are not used on this site.

When to pick may-minihttp instead

Pick may-minihttp when

  • HTTP/1.1 is all you serve and you want the most requests per second: in campaign 4 it answered 6-16% more status requests than simoom, and its program is 515 KB against 735 KB for simoom's default build.
  • Your network path is unreliable: in an earlier campaign (2026-11-11) it held up best on a droplet with a degraded network path. Campaign 4 did not test that case.
  • You are comfortable with stackful coroutines. Whether they can be made fully sound in Rust is an open discussion; read it and decide for yourself.

Pick simoom when

  • You need HTTP/2, HTTP/3, TLS, WebSocket or a client in the same program.
  • CPU, latency or memory matter more than peak throughput: in campaign 4 simoom used 15% less CPU per request, held 35x less memory per idle connection and started 8.9x faster.
  • You want strict, bounded parsing: every limit has a default, h2spec 146/146, HTTP Garden with 0 desyncs.
  • You want blocking work handled for you: a bounded offload pool that answers 503 instead of queueing forever.
  • You want no third-party crates at all, and unsafe confined to one crate.

How it was measured

Setup

  • DigitalOcean c-4 droplets (4 dedicated vCPUs, Xeon Platinum 8280, Bangalore), Ubuntu 24.04.
  • One server droplet and two load droplets; open-loop load at fixed rates.
  • may-minihttp 0.1.11 from its pinned Cargo.lock.

Rules

  • Headline: the highest steady rate whose p99 stays at or under 1 ms.
  • Campaign 4, 2026-11-12: simoom ran on the same droplet in the same round as may-minihttp; every figure is the median of rounds.
  • Raw HDR logs, scripts and analyses are in bench/results/.

Common questions

What is a good may-minihttp alternative?

If you like may-minihttp for its throughput without tokio but need more than HTTP/1.1, simoom covers HTTP/1.1, HTTP/2, HTTP/3, its own TLS 1.3, WebSocket and a client with no third-party crates. On the same droplet in benchmark campaign 4 (2026-11-12), may-minihttp answered 6% more status requests per second at 256 clients and its program is smaller (515 KB against 735 KB for simoom's default build), while simoom used 15% less CPU per request, started 8.9x faster and held 35x less memory per idle connection. If you want a framework on tokio instead, look at axum or xitca-web.

Is may-minihttp faster than simoom?

On plain throughput, yes. In benchmark campaign 4 (2026-11-12), with both servers on the same droplet in the same rounds, may-minihttp answered 15%, 6% and 16% more status requests per second than simoom at 64, 256 and 1,024 clients, and 5% more on the 1 KB JSON API. simoom had the lower p99 at a fixed 50,000 req/s (355 µs against 400 µs), used less CPU per request (23.4 µs against 28.2 µs) and answered 30% more requests within 1 ms during a traffic spike. may-minihttp's program is also smaller: 515 KB against 735 KB for simoom's default build.

What is the fastest Rust HTTP server?

There is no single answer: it changes with the machine, the number of connections and the test. In benchmark campaign 4 (2026-11-12), with each server on the same droplet as simoom, may-minihttp led the status endpoint at 256 clients with 154,590 req/s, 6% more than simoom; simoom came second of 19, 24% ahead of hyper. simoom was first of 19 on CPU per request and first of 8 on HTTPS throughput, H2O led HTTP/2 and HTTP/3, and actix-web led the traffic spike. Measure on your own hardware with your own traffic.

Does may-minihttp support HTTP/2 or TLS?

may-minihttp is a minimal HTTP/1.1 server, best known from benchmarks. simoom adds HTTP/2, HTTP/3 over QUIC, TLS 1.3, WebSocket and server-sent events as cargo features, and an HTTP/1.1-only build is available when that is all you need.

Quick start

For an HTTP/1.1-only build like may-minihttp's, turn simoom's default features off.

# Cargo.toml
simoom = { version = "0.1", default-features = false, features = ["http1"] }

simoom

A small, fast HTTP/1.1, HTTP/2 and HTTP/3 server engine you build into Rust programs, with its own TLS 1.3 and nothing but the Rust standard library underneath. The HTTP engine of Cameleer.
