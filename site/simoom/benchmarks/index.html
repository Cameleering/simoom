How it was measured

Machines and load

  • Server: DigitalOcean c-4 droplets, 4 dedicated vCPUs (Xeon Platinum 8280), Bangalore region, Ubuntu 24.04. Their NIC has one receive queue.
  • Load: two separate load droplets, open loop: requests are sent at a fixed rate whatever the server does, so a slow server can't slow the load down and hide its own latency (no coordinated omission).
  • Same droplet only: droplets of the same type differed by up to 7x for every server, so a comparison always uses one droplet.

What is counted

  • Headline figure: the highest steady rate at which 99% of answers arrive within 1 ms (the "SLO throughput"), verified by longer runs after the search.
  • S1: a GET with a 13-byte answer, one request in flight per connection, at 64, 256 and 1,024 connections.
  • Versions: hyper 1.12.0, may_minihttp 0.1.11, xitca-web 0.7.1, h2o 2.3.0-DEV, nginx 1.24.0, haproxy 2.8.30.

Raw HDR logs, scripts and analyses are in the repository: bench/results, scripts in bench/cloud, competitor programs in bench/competitors.

Where simoom is behind

Losses are part of the result.

  • Heavy overload. At 195k req/s offered, 1.17 times what the droplet's network card carries, simoom answers the most requests in total (160.3k against nginx's 145.5k), but nginx answers far more of them within 1 ms (52.4k against 6.4k). nginx's figure changed 20-fold between droplets, so it is recorded as a limit of the test at that rate (issue K13).
  • A degraded network path. On a droplet with a slow network path, may-minihttp kept 114.7k req/s while simoom and the other servers fell to 17–62k. The interrupt-placement fix (K12) has not been rerun on such a droplet.
  • A new connection for every request. On one droplet simoom handled 19.3k connections per second against xitca's 24.3k (−21%). On another, simoom led with 22.1k against hyper's 19.3k.
  • Slow attackers. With 10,000 slowloris and 1,000 slow-read attackers, simoom's p99 for real requests was 8% above haproxy's (784 µs against 724 µs).
  • Idle memory with TLS is 3.3% above Cameleer's old server (1,360 KB against 1,317 KB).
  • Executable size: the HTTP/1.1-only executable is 4% larger than may-minihttp's.
  • Coverage: every cloud figure comes from 4-vCPU droplets with a single-queue network card. Larger machines and multi-queue NICs have not been measured.

Common questions

What is the fastest Rust HTTP server?

It depends on the scenario and the machine. In simoom's runs on one 4-vCPU DigitalOcean droplet, simoom led plain HTTP at 64 and 256 connections and over TLS, io_uring simoom led at 1,024 connections, and may-minihttp held up better on a degraded network path. Numbers from different machines should not be compared: droplets of the same type differed by up to 7x.

Why p99 under 1 ms instead of maximum requests per second?

A server that answers more requests but makes some of them wait seconds is not faster for the people waiting. The headline figure is the highest steady rate at which 99% of answers arrive within 1 ms, with the load sent at a fixed rate so a slow server cannot slow the load down and hide its latency.

Why are only servers on the same droplet compared?

Droplets of the same type differed by up to 7x for every server, and one had a degraded network path for all of them. A comparison across droplets would measure the machines, not the servers.

Can I rerun the benchmarks?

Yes. The scripts are in bench/cloud in the repository, the competitor programs in bench/competitors, and the raw HDR logs, tables and analyses in bench/results. scripts/size.sh reproduces the size table.

Has anyone else measured simoom?

Not yet. Every figure here was measured by the project. If you measure it differently and get a different number, open an issue with your method.

simoom

A small, fast HTTP/1.1, HTTP/2 and HTTP/3 server engine you build into Rust programs, with its own TLS 1.3 and nothing but the Rust standard library underneath. The HTTP engine of Cameleer.

simoom is a Cameleering project: carry more on less, no claim without a number.
