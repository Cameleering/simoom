## Incident: about 77 idle droplet-hours

- The lanes finished at 18:25-18:28 UTC. The operator's machine restarted during the run; the
  background `follow` pulls and the operator session died with it.
- The safety net was armed (`safety-net.sh arm 3.5`, fire at 20:25 UTC) but **never fired**:
  - the watcher was a process of the operator's session and died with the restart;
  - the scheduled task was registered for the logged-on user only and never ran
    (`LastTaskResult 267011`, "has not yet run"; no missed run counted).
- The coordinator found the droplets idle the next morning, fetched every lane completely and
  deleted them at 02:57 UTC: **9 x c-4 for 10.0 h = about 90 droplet-hours (about $11), of which
  about 77 idle**. Campaign 2 used about 24.
- **Fix (this commit, `bench/cloud/safety-net.sh` and `campaign-ctl.sh`):**
  - the task's action is now `safety-net.sh due` (fire only if the armed deadline has passed), and
    the task also triggers **at every logon** of the user, so a restarted machine fires an overdue
    net as soon as the user logs in;
  - every `campaign-ctl.sh` command except `down`, `merge` and `sh` runs `safety-net.sh due` first,
    so the operator's next action after an interruption deletes overdue droplets before anything
    else;
  - the DigitalOcean token still never leaves the workstation (no remote self-destruct; a
    powered-off droplet is still billed, so a remote `shutdown` would not help either).
  - Checked: arming registers both triggers (`MSFT_TaskTimeTrigger`, `MSFT_TaskLogonTrigger`), and
    `due` with a past deadline runs the full fire path (with no droplets left it deleted only the
    leftover `simoom-bench-key`, which `down` had missed because the coordinator's state directory
    lacked `uploaded-key-id`).
- Remaining risk: a workstation that stays off with nobody logging in. Keep it awake during a
  campaign, and check the DigitalOcean console after any interruption.

## Campaign 2's losses, one by one

**1. S1 at 256 connections (K4): level on the clean droplet, behind on the median.**
- srvB, the clean droplet: simoom-uring 166.9k, may-minihttp 163.9k, hyper 162.8k: a tie. The
  epoll builds stay where campaign 2 had them: simoom 140.2k, simoom-default 142.2k,
  simoom-builder 137.8k (-14%).
- Medians over the three droplets: simoom-uring 115.4k against may-minihttp 163.9k (-30%), because
  may-minihttp kept 114.7k on srvC and 167.5k on srvA where the simoom variants fell to 38-115k.
- The RTO hypothesis is **not confirmed**: passing runs show more retransmits than failing ones
  (may-minihttp 9,900-10,300 segments in its passing srvA/srvB rounds, hyper 12,800, simoom-uring
  7,400 on srvB; simoom 1,500-3,700 in its failing rounds). simoom's failing points have p50
  180-210 µs and p99 1.2 ms to hundreds of ms: a tail of a few slow connections, not loss.
- Hypothesis: on a noisier path a stalled loop turn delays every connection of that loop at once,
  while may-minihttp's coroutine per connection spreads the stall. K4's early flush
  (`Driver::flush_now`, epoll only) did not move the epoll figure on srvB (140k against campaign
  2's 138k median). Next: the same-droplet A/B (28d2a6f, 1e50579, and 28d2a6f with
  `FLUSH_EARLY_BATCH = usize::MAX`), plus per-loop latency histograms to see whether slow requests
  cluster per loop.

**2. S9 overload (K5): now comparable; simoom answers the most but not in time.**
- At 195k req/s offered (above the 165k NIC ceiling) simoom-uring has the highest goodput of any
  server (160.3k), and in-time goodput level with hyper on the same droplet (6.4k against 6.1k).
- nginx answers fewer (145.5k) but 52.4k within 1 ms (admitted p99 4.7 ms); everyone else sits at
  admitted p99 about 210 ms, the minimum RTO.
- K5's bound covers deferred and offloaded replies only; inline handlers rely on the kernel queues,
  and at 1.17 x the NIC ceiling every admitted request then waits. Hypothesis: nginx's workers
  accept and read less per loop turn, so the excess waits in the listen backlog instead of in
  established sockets. An opt-in read-side bound for inline handlers (stop reading new requests
  while a loop's unsent output or turn time is over a bound) would test it.

**3. S1 at 1024 connections: lead lost.** simoom-uring 138.6k on srvB is within 4% of its
campaign-2 value (143.9k), but hyper reached 166.9k on the same droplet (115k in campaign 2). srvA:
simoom (epoll) 79.4k, may-minihttp 100.2k, xitca 0 verified. simoom itself did not move beyond the
4% bracket, so this is not recorded as a simoom regression; the hyper figure shows what a clean
droplet allows.

**4. S5 connection per request: split.** srvB: simoom-uring 22.1k ahead of hyper (19.3k) and h2o
(18.7k). srvA: simoom (epoll) 19.3k against xitca 24.3k and cameleer 24.2k (-21%); campaign 2 had
the epoll build at 23.7k on its droplet. Not separable from the droplet; campaign 2's proposal
(batched `accept4`, fewer epoll waits per connection) stands.

**5. S10 slow attackers (K6): churn fixed, small tail gap left.** simoom holds all 10,000 slowloris
and 1,000 slow readers open (closed by the server: 0, was 68,409), like haproxy. The attack raises
simoom's legitimate p99 by 356 µs (428 to 784 µs) against haproxy's 366 µs (358 to 724 µs) on the
same droplet: the remaining -8% is simoom's baseline tail on srvA. simoom-uring on srvB: 272 to
517 µs. nginx (srvC): 419 to 458 µs, but it closes every slowloris. simoom sent 76.6 MB to the slow
readers in the window against haproxy's 1.2 MB (it keeps their 64 KB responses flowing).

**6. Idle memory (K7): fixed.** simoom-default 951-1,002 KB against cameleer-http-min's
1,146-1,192 KB on the same droplet in all three rounds (cgroup memory 328-336 KB against 412-416
KB). The like-for-like plain/TLS check is below.

**7. Memory per idle connection (K8): fixed at 100k, -12% at 10k.** simoom 594 B at 10k and 533 B
at 100k (campaign 2: 913 / 737); simoom-default 596 / 520; nginx 522 / 532; io_uring 814 / 692.
cameleer-http-min shows 3,368 B at 10k but 407 B of PSS at 100k; its cgroup memory, which counts
kernel socket buffers, is 424 MB at 100k against simoom's 217 MB and nginx's 276 MB, so the 407 B
figure understates it.

**8. Size (K9): near tie.** The http1-only `min_server-h1` is 536 KB stripped against
may-minihttp's 515 KB (-3.9%); about 181 KB of either is std's backtrace symbolizer (K9). The
default-feature `min_server` is 734 KB, the full campaign server 1,545 KB.

**9. S4 and S8: ties at the NIC**, as before.

## Start-up and memory against cameleer-http (plan §0 item 7, release gate)

- Cold start: plain -5%, TLS -37%: **pass**.
- Idle memory, plain: +0.1%: **pass**.
- **Idle memory with TLS: +11% PSS (+146 KB), +7% RSS: outside the 5% rule** (BUGS K11). This
  was already outside on 2026-11-09 (+8-9%, `docs/STATUS.md` "Start-up and memory against
  cameleer-http"), where the difference was file-backed code pages touched at start, not
  anonymous memory, and the measured advantage that the rule asks for is documented (1.7-1.8x

  both TLS builds after one handshake, to confirm it is still code pages; the owner decides whether
  the documented advantage covers it.
- On the droplets (lane 3, same droplet per round): simoom-default 0.96 MB idle against
  cameleer-http-min (TLS configured) 1.15 MB; cold start simoom-default 1.05 ms against
  cameleer-http-min plain 1.25 ms and with TLS 2.07 ms. `min_server` on srvA: 0.91 ms plain,

## Bugs and regressions

- **K11 (release gate, known since 2026-11-09 at +8-9%):** idle PSS with TLS now 11% above
  cameleer-http with TLS (above).
