Why an earlier round read differently

In campaign 3 (2026-11-11), may-minihttp led simoom at 64 and 256 connections. Both rounds stay published; the newer one supersedes the older for plain HTTP.

What was wrong

  • The droplet's network card has one receive queue, so one CPU spends much of its time on network interrupts.
  • simoom's loops were not kept off that CPU. The scheduler kept placing a loop there, and every connection that loop held waited for it: p99 went to hundreds of milliseconds while the other CPUs had room.
  • may-minihttp and hyper also ran on that CPU, but their other threads took the work over.

What changed

  • The loop threads now stay off the CPU with the most network-interrupt time (bug K12 in the repository).
  • Plain HTTP with epoll went from 117.0k / 133.8k / 87.6k to 170.6k / 172.6k / 138.6k at 64 / 256 / 1,024 connections on the same droplet.
  • The fix has not been rerun on a droplet with a degraded network path, where may-minihttp was the most robust server.

On campaign 3's cleanest droplet (srvB), simoom's io_uring back end was already level with may-minihttp at 256 connections (166.9k against 163.9k). Analysis: bench/results/2026-11-12-epoll/analysis.md and 2026-11-11-campaign3/analysis.md.

When to pick may-minihttp instead

Pick may-minihttp when

  • HTTP/1.1 is all you serve, and you want the smallest, rawest server for a throughput test.
  • Your network path is unreliable: it held up best on the degraded droplet.
  • You are comfortable with stackful coroutines. Whether they can be made fully sound in Rust is an open discussion; read it and decide for yourself.

Pick simoom when

  • You need HTTP/2, HTTP/3, TLS, WebSocket or a client in the same program.
  • You want strict, bounded parsing: every limit has a default, h2spec 146/146, HTTP Garden with 0 desyncs.
  • You want blocking work handled for you: a bounded offload pool that answers 503 instead of queueing forever.
  • You want no third-party crates at all, and unsafe confined to one crate.

How it was measured

Setup

  • DigitalOcean c-4 droplets (4 dedicated vCPUs, Xeon Platinum 8280, Bangalore), Ubuntu 24.04.
  • One server droplet and two load droplets; open-loop load at fixed rates.
  • may-minihttp 0.1.11 from its pinned Cargo.lock.

Rules

  • Headline: the highest steady rate whose p99 stays at or under 1 ms.
  • Only servers on the same droplet are compared; the analysis names the droplet for every campaign-3 figure.
  • Raw HDR logs, scripts and analyses are in bench/results/.

Common questions

What is a good may-minihttp alternative?

If you like may-minihttp for its throughput without tokio but need more than HTTP/1.1, simoom covers HTTP/1.1, HTTP/2, HTTP/3, its own TLS 1.3, WebSocket and a client with no third-party crates. On the same droplet on 2026-11-12 it led may-minihttp by 8% at 64 connections and 15% at 256. If you want a framework on tokio instead, look at axum or xitca-web.

Is may-minihttp faster than simoom?

It depends on the round and the droplet. In the 2026-11-12 round, simoom led at 64, 256 and 1,024 connections in every round. In the earlier campaign of 2026-11-11, before simoom's fix for loops sharing a CPU with the network card's interrupts, may-minihttp led at 64 and 256 connections. may-minihttp also held up far better on a droplet with a degraded network path, and its executable is 4% smaller.

What is the fastest Rust HTTP server?

There is no single answer: it changes with the machine, the network path, the number of connections and the test. On one 4-vCPU droplet on 2026-11-12, simoom served 172,638 plain requests per second with p99 under 1 ms at 256 connections, may-minihttp 150,673 and hyper 144,443. On a droplet with a degraded network path, may-minihttp was the most robust. Measure on your own hardware with your own traffic.

Does may-minihttp support HTTP/2 or TLS?

may-minihttp is a minimal HTTP/1.1 server, best known from benchmarks. simoom adds HTTP/2, HTTP/3 over QUIC, TLS 1.3, WebSocket and server-sent events as cargo features, and an HTTP/1.1-only build is available when that is all you need.

Quick start

For an HTTP/1.1-only build like may-minihttp's, turn simoom's default features off.

# Cargo.toml
simoom = { version = "0.1", default-features = false, features = ["http1"] }

simoom

A small, fast HTTP/1.1, HTTP/2 and HTTP/3 server engine you build into Rust programs, with its own TLS 1.3 and nothing but the Rust standard library underneath. The HTTP engine of Cameleer.
