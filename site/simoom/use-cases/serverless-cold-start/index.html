Serverless and scale to zero

An HTTP layer that isn't your cold start

A function that scales to zero pays for its start-up on every cold request, and pays for its memory every second it runs. simoom gives the first answer 0.73 ms after the process starts and idles at about 1 MB, so the time and the memory go to your code.

Start-up, measured

Cold start is the time from spawning the process to the first successful answer on its port. Each comparison ran on one machine, with both servers returning the same 13-byte answer.

simoom0.73 ms0.87 ms1,018 KB plain · 1,360 KB TLS
Cameleer's old server (cameleer-http)0.77 ms1.37 ms1,017 KB plain · 1,317 KB TLS

WSL2, 10 alternating rounds, 2026-11-11 (TLS memory after the K11 fix, 2026-11-12). With TLS and HTTP/3 together, simoom's start was 1.91 ms (P-256), because HTTP/3 servers start every loop at once. The platform's own sandbox start comes on top for every runtime. Details: benchmarks.

Why it starts fast

Less to set up

  • No async runtime to build before the first request.
  • Lazy loops: start returns with one loop running; the others start in the background once that loop gets busy.
  • The descriptor table is grown once at start, not while threads run.
  • A P-256 key's signing table is built on the first signature, not at load.

Less to carry

  • An HTTP/1.1-only build adds 215 KB; the full server with HTTP/3 adds 935 KB.
  • Nothing from crates.io, so nothing extra to download, compile or ship.
  • One event loop per CPU core, so a small function with one vCPU runs one loop.

The start-up work behind these numbers is described in runtime. Build options: features and size.

A function's HTTP server

Container platforms such as Cloud Run send requests to a port; listen on it and answer. A graceful stop tells clients to finish when the platform retires the instance.

use simoom::{Backend, Reply, Request, Server};
use std::time::Duration;

let server = Server::builder()
    .listen("0.0.0.0:8080")
    .threads(2)               // 0 = one loop per core (the default)
    .backend(Backend::IoUring) // Linux 6.1+, falls back to epoll
    .service(|_: &mut Request<'_>, r: Reply<'_>| r.body_static(b"ok"))
    .start()
    .unwrap();
// ...
server.stop(Duration::from_secs(5)); // tells clients to finish, then waits up to 5 s
server.join();

simoom serves HTTP on a socket. On AWS Lambda that means a container image or an HTTP adapter in front of the port: simoom does not speak the Lambda Runtime API itself. Cameleer, which uses simoom, is its own Lambda runtime: see Cameleer on AWS Lambda.

Common questions

What is the smallest Rust web server for AWS Lambda or other serverless platforms?

An HTTP/1.1-only simoom build adds about 215 KB to a binary, gives the first answer 0.73 ms after the process starts and idles at about 1 MB. Turn off the default features and keep http1.

Does simoom speak the AWS Lambda Runtime API?

No. simoom serves HTTP on a socket, which suits container platforms such as Cloud Run directly. On Lambda it runs behind an adapter or in a container image. Cameleer, which uses simoom as its HTTP engine, is its own Lambda runtime.

How fast is the cold start with TLS?

0.87 ms from process start to the first answer with a P-256 certificate, against 1.37 ms for Cameleer's old server on the same machine. With HTTP/3 enabled as well it was 1.91 ms.

Do I need tokio for a serverless HTTP handler in Rust?

No. simoom has no async runtime. A service is a plain function; slow work goes to a bounded offload pool or to your own threads.

How much memory does an idle simoom server use?

About 1 MB of PSS after one request: 1,018 KB plain and 1,360 KB with TLS, measured on WSL2.

Measure it yourself

Build the hello example in release mode and time the first answer on your platform.

cargo add simoom
cargo run --release -p simoom --example hello -- 127.0.0.1:8080   # from a checkout of the repository
